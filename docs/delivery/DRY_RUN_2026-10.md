# Pilot dry run, October 2026: can a client start within 7 days of "yes"?

Run on 2026-10-10 with made-up data, on the real code, the real database
and the real webhook server. A fake GoHighLevel wrote a log instead of
texting anyone. Nothing left the machine.

Re-run it any time (about 30 seconds; needs Docker Postgres up):

```bash
.venv/Scripts/python.exe -m delivery.dry_run
```

It leaves a pilot `dryrun-windows-<yyyymm>-1` in the database (state
`live`) and these files in `clients/dryrun-windows/` (gitignored):
`old_quotes.xlsx` / `.csv` (315 messy rows), `dnc.csv`, `audit.md`,
`approved_messages_v1.txt`, `ghl_dry_run.jsonl` (every call GHL would have
received), `invoices/VQ-*.md`, `reports/<week>.md`, `dry_run_timings.md`.
Try `pilot status`, `pilot report`, `pilot invoice` on it. Re-running
deletes and rebuilds it. The same path is a test:
`tests/integration/test_dry_run.py` (VELARQO_DB_TESTS=1).

**Result: the path runs end to end.** 9 code bugs found and fixed (section
3). The code is not what stops a 7-day start; the GoHighLevel build, the
signed documents and the webhook endpoint are (section 4).

## 1. The fake installer

"Dry Run Windows Ltd", 315 rows as a real spreadsheet would be: dates in
five formats plus "TBC", phones as `07700 900123`, `+44 7700…`, Excel-mangled
`7700900123`, landlines, blanks; values as `£3,450`, `3450.00`, `approx 5k`;
statuses from "Lost" to "Deposit paid" to "DEAD"; sources incl. Checkatrade,
Bark, MyBuilder, bought leads and blanks; opt-outs as "Y", "yes", "DO NOT
CONTACT"; the same person twice (same mobile, or email-only on the second
quote); one exact duplicate row; a blank row; a TOTAL row. Plus their
do-not-contact list (8 entries, 6 overlapping the export).

What came out:

| Stage | Count |
|---|---:|
| Rows in the export | 315 |
| Sample audit: "worth chasing" (date 3-24 months, not won, not opted out) | 169 |
| Import: eligible after source, contact details, area, DNC list, one row per person | 55 |
| Held back as comparison group (15%) | 8 |
| To contact | 47 |

Lesson for the real thing: **a 300-row export is about 50 contactable
people.** Lead-site rows (74 here) and blank sources (10) are the big cuts.
Ask for *every* quote from the last 24 months, not "a few hundred", and
ask on the call how many came through Checkatrade/Bark.

auth); a duplicate delivery was recognised and ignored; an appointment on
the installer's own calendar was logged only; a STOP was pushed to GHL as

**Calendar days, best case:** yes on day 0, canary on day 6, live on day 7.
Every slip is the installer (signing, export, message approval) or the GHL
number. The code path from "export in hand" to "canary sent" is under 2
minutes of commands.

## 3. What broke, what was manual, what was slow

Fixed in this run (all have tests):

1. **Excel files crashed the audit**: `openpyxl` wasn't installed although
   the audit says it reads `.xlsx`. Added to `pyproject.toml`.
2. **"Customer" and "Quote £" columns were ignored**, so the homeowner's
   name and the quote value never reached the database or GHL ("Hi ," in
   the text). Header matching now strips £/brackets and knows installer
   headers (customer, client, homeowner, job value…).
3. **ISO dates (`2026-03-12`) were read day-first as 3 December.** CRMs
   export ISO. Every age bucket was wrong for those rows.
4. **Excel serial numbers** (`46093`) in a CSV were read as 1970. Now a date.
5. **"Johnson, Gary" became first name "Johnson,"**: the text would open
   "Hi Johnson,". Names in "Last, First" and "Mr G Johnson" form are split
   properly now.
6. The audit's age table showed won/opted-out rows as "unknown date" (127
   of 315); now every dated row is aged.
7. pandas printed a warning per date; silenced.
8. Invoice lines showed the survey as `2026-10-14T10:00:00Z`; now
   "14 Oct 2026, 11:00" UK time.
9. My own harness bugs (survey outcomes sent for the wrong contact; SQL).

Built because it didn't exist:

- **`pilot report`**: the weekly report (`10_weekly_report_template.md`)
  filled from the database, counts of people only. Rows the code can't know
  ("interested") are left out. The left-alone group's bookings show "not
  recorded yet": there is no command to log a holdout person who came back
  on their own; the installer has to tell us and for now it goes in the
  report by hand.
- **Dry-run mode for GHL** (`GHL_DRY_RUN=1`): only for pilots whose
  location id starts with `dry-`, so a real pilot can never be marked
  "enrolled" without texts going out.
- **`scripts/pilot_check.cmd`** for Task Scheduler every 15 minutes.
  Nothing scheduled `pilot check` before.

Manual steps that stay manual (by design or for now):

- Copying counts from `audit.md` into the 03 email (5 min). Fine.
- Copying the approved texts into `approved_messages_v1.txt` and into the
  GHL workflow, by hand, twice. Risk: a typo in GHL that isn't in the
  approved file. Mitigation: paste from the file, then read the workflow
  back once.
- `pilot set` from the signed agreement; `pilot log manual_minutes`
  weekly; `pilot optout` for opt-outs the installer hears about.
- Filling the bracketed lines of the report and the invoice header
  (supplier details, VAT wording, payment terms, bank details).
- Removing GHL tags when a pilot is cancelled.

Slow or surprising:

- **Thresholds bite early.** Wave 2 had 22 people; 3 opt-outs (14%) and 2
  complaints paused the pilot, as designed. With waves of 20-30, one
  grumpy reply is 4%. Expect a pause or two in week 1 and be reachable to
  review and resume the same day, or the installer sees nothing happen.
  The thresholds in `WORKFLOW.md` section 5 still need Pablo's written yes.
- **Wave 2 asked for 60 and got 22**: the list ran out. With ~50 contactable
  people a pilot is one canary plus one wave. Size the cap and the
  "weekly" promise to the real list, not to the agreement template.
- Email-only people (no UK mobile) are pushed and tagged like everyone
  else. The GHL workflow must branch: no phone → send the email only.
- Invoice numbers come from a global counter shared with test runs: the
  first real invoice will be about VQ-00160, not VQ-00001. Cosmetic; change
  to per-client numbering before the first real invoice if it matters.
- First import generates `VELARQO_KEY_SECRET` into `.env`. **Back it up**
  with the rest of `.env`: a new secret means every homeowner key changes.
- The database lives on Pablo's PC. During this run another session's
  tests made one step take 50 s instead of 0.3 s. A 15-minute check and a
  webhook receiver on a laptop that sleeps is the weakest link until the VPS.

## 5. Day 0 → day 7 checklist

Day 0 = the installer says yes (or agrees to the no-export start,
`SALES_PLAYBOOK.md` section 3).

- [ ] **Day 0** Send `02` (export request) within the hour. Start the GHL
  trial; request the UK number. `pilot create`. Book the 15-min call for
  day 2. Ask on the call: how many quotes came via Checkatrade/Bark?
- [ ] **Day 1** Sample in → `sample_audit` → `03` email with the counts.
  `advance sample_received`, `advance audited`. If under ~100 look worth
  chasing, say so and ask for the full 24 months before going further.
  Start the GHL sub-account build (copy the snapshot if one exists).
- [ ] **Day 2** Call: price, cap, holdout, booked-survey definition. Send
  `04` + `05` for signature and `07` intake form the same hour.
- [ ] **Day 3** Signed → `pilot approve … agreement`, `advance agreement_signed`.
  Full export + DNC list in → `advance data_received`, `pilot import`,
  `pilot freeze`, `pilot set` (price, caps, GHL ids once known). Send `09`
  (message sheet). If the export is late, chase once by phone, not email.
- [ ] **Day 4** Messages ticked → `approved_messages_v1.txt`, `pilot approve …
  messages --messages-file`, `advance messages_approved`. Paste the same
  texts into the GHL workflow. Calendar + webhook action set up;
  `VELARQO_WEBHOOK_SECRET` set; webhook server + tunnel running;
  `scripts/pilot_check.cmd` scheduled.
- [ ] **Day 5** Own-phone test and dead-number test; run the GHL
  verification list; thresholds confirmed. `advance canary_ready`,
  `pilot approve … canary_go`, `advance canary_running`.
- [ ] **Day 6** `pilot send-wave <id> w1 --size 25`. Answer replies within 1
  working hour. Watch `data\pilot_check.log`.
- [ ] **Day 7** Canary review: STOPs, complaints, delivery failures,
  bookings vs the stop conditions. `advance canary_reviewed`, `pilot approve
  … go_live`, `advance live`, `send-wave w2`. Diary the Monday invoice +
  report.

If any of items 1-4 in section 4 isn't ready by day 5, day 6 moves; the
installer should hear that on day 5, not day 6.
